# httpee — архитектура пакета

Пакет `httpee` — тонкая обёртка над fetch.py: функции-глаголы и функции-модификаторы,
спроектированные под eelang-пайплайны (`..f(x)` = `f(x, значение)`). Здесь — границы,
семантика и решения; «что и зачем» — в `httpee-client`.

## Компоненты

- **`httpee/__init__.py`** — весь публичный API: глаголы `GET`, `POST`, `PUT`, `PATCH`,
  `DELETE`, `HEAD`, `OPTIONS` и `fetch`; модификаторы `headers`, `query`, `timeout`,
  `json`, `data`, `method`, `url`; `httpee()` — конструктор пустого запроса; `Response`
  и исключения (`Error`/`RequestError`/`Timeout`/`HTTPError`) — реэкспорт из fetch.py.
- **`httpee/_fetch.py` (вендор)** — fetch.py целиком, без изменений (MIT © Kenneth
  Reitz; на PyPI его нет, сам файл рекомендует копирование в проект).
- **`_Request` (внутренний)** — накапливаемое состояние запроса: `method`, `url`,
  `json_body`, `data_body`, `headers`, `params`, `timeout`. Пользователю не виден;
  создаётся только `httpee()`.
- **Выполнение** — глагол зовёт `fetch.request(..., check_status=False)`: временная
  сессия на запрос, как модульный API requests.

## Семантика

- **Модификатор** `..f: x` = `f(x, значение)`: на `_Request` — дополняет; любое другое
  значение пайплайна — `TypeError` (запрос начинается с `httpee()`). Модификаторы
  повторяемы и в любом порядке перед глаголом. Применение после глагола (на `Response`)
  — `TypeError` с внятным сообщением.
- **Глагол** `..GET: url` = `GET(url, значение)`: выполняет запрос. Тело — `..json:`
  (JSON) или `..data:` (mapping → form-encoded, str → текст, bytes → сырые); content-type'ы
  ставит fetch.py (setdefault — пользовательский не перетирается); оба вместе — `ValueError`.
- **`Response`** — `fetch.Response` (поле `status` уже есть, паттерн `Response(status=200)`
  работает class-паттерном как есть). Остальное — родное: `.json()`, `.text`, `.headers`,
  `.raise_for_status()`.
- **`..fetch()`** = `fetch(значение)`: выполняет запрос с заранее заданными `..method:`
  (по умолчанию GET) и `..url:` (обязателен — без него `TypeError` с внятным сообщением).
  Глагол в конце (`..GET:`) переопределяет ранее заданный метод и выполняет сразу.
- **4xx/5xx не кидаются** — `check_status=False`; статус проверяет `..assert:`/`..match:`
  (провал ассерта — `MatchError` из eelang, не из пакета). Редиректы следуются
  (до 10, как в fetch.py). Сетевые ошибки и таймауты — исключения fetch.py как есть.

## Решения и инварианты

- **Никакого глобального состояния.** Каждый запрос — временная сессия fetch.py (как
  модульный API requests); переиспользуемые сессии — вне v1.
- **Только sync.** fetch.py (urllib, HTTP/1.1), никаких потоков и event loop'ов; работает
  под monkey-patched gevent (блокирующие сокеты).
- **Пакет — обычный Python, eelang не импортируется.** Пайплайновость даёт язык на месте
  вызова; внешних зависимостей нет — fetch.py завендорен как `httpee/_fetch.py`.
- **Имена — часть контракта:** глаголы-методы ЗАГЛАВНЫМИ (совпадают с HTTP-методами),
  `fetch` и модификаторы — строчные английские слова. Изменение имён ломает пайплайны.
- **Таймаут по умолчанию** — fetch.py'евский (30 c); `..timeout:` переопределяет на запрос.
- **Два файла.** `httpee/__init__.py` + вендор `httpee/_fetch.py`; дробить больше нечего.

## Границы

- Внешних зависимостей нет; eelang нужен лишь для запуска `.eel`-скриптов.
- Не поднимает ошибок на 4xx/5xx — это контракт для `..assert`/`..match`.
- Вне v1: сессии (`..using:`), async, retry, streaming, загрузка файлов — см. `httpee-client`.
